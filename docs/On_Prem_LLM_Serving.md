## 1. 왜 On-Prem이 뜨고 있나

### 배경

국내 금융권·대기업을 중심으로 AI 서비스를 **자체 인프라(On-Premise)** 에 구축하려는 수요가 빠르게 늘고 있습니다. 이유는 단순합니다.

**클라우드 LLM API를 쓸 수 없는 이유들**

| 이유 | 설명 |
|------|------|
| **데이터 외부 반출 금지** | 고객 정보, 내부 문서, 계약서 등이 회사 외부 서버로 나가는 것 자체가 내부 규정·법령 위반 |
| **금융감독원 규제** | 금융 데이터를 외부 클라우드에 올리려면 별도 심사가 필요하며, 통과되더라도 데이터 잔류 이슈 존재 |
| **보안 감사 대응** | 데이터가 어디 저장되는지 추적해야 하는 요구사항 — 클라우드 API는 블랙박스 |

즉, **"On-Prem을 선택하는 것"이 아니라 "클라우드를 선택할 수 없어서" On-Prem으로 가는 경우**가 대부분입니다.

### On-Prem AI의 현재 위치

```
[클라우드 API 시대]           [On-Prem 전환 시작]         [On-Prem 성숙]
OpenAI/Claude API로  →  데이터 보안 이슈 인식  →  자체 GPU 서버 + 오픈소스 LLM
빠르게 프로토타입             On-Prem 검토 시작            내재화 및 최적화
```

현재 많은 기업이 **"전환 시작"** 단계에 있으며, 가장 뜨거운 질문은 이것입니다:

> "클라우드에서 GPT-4/Claude로 만든 Agentic RAG 시스템을,  
>  On-Prem 오픈소스 모델로 그대로 재현할 수 있을까?"

이 문서는 그 질문에 대한 **현장 경험 기반의 솔직한 답변**입니다.

## 2. 하드웨어 현실: GPU와 VRAM 계산법

### LLM 서빙에 GPU가 필요한 이유

LLM은 수십억~수천억 개의 **가중치(파라미터)** 를 저장하고 매 추론마다 이를 연산합니다. 이 규모의 행렬 연산은 CPU로는 현실적인 응답 속도를 낼 수 없고, **고대역폭 메모리(HBM)를 탑재한 GPU/NPU** 가 필수입니다.

### VRAM 요구량 빠른 계산법

모델을 올리는 데 필요한 최소 VRAM을 추정하는 공식:

```
필요 VRAM(GB) ≈ 파라미터 수(B) × 정밀도 바이트 수 × 1.2 (추론 오버헤드)

예시:
- 70B 모델, FP16(2바이트) → 70 × 2 × 1.2 ≈ 168GB
- 70B 모델, INT4 양자화(0.5바이트) → 70 × 0.5 × 1.2 ≈ 42GB
```

**정밀도(Precision)별 특성**

| 정밀도 | 바이트/파라미터 | 특징 | 권장 용도 |
|--------|----------------|------|-----------|
| **FP32** | 4바이트 | 최고 정확도, 메모리 최대 | 학습용, 서빙에는 과함 |
| **FP16/BF16** | 2바이트 | 정확도 거의 동일, 절반 메모리 | 프로덕션 기본 선택 |
| **INT8** | 1바이트 | 약간의 품질 저하 | 메모리 부족 시 타협점 |
| **INT4 (양자화)** | 0.5바이트 | 체감 가능한 품질 저하 | 소규모 GPU 환경, 데모용 |

### GPU별 스펙 비교

| GPU | VRAM | 아키텍처 | 비고 |
|-----|------|----------|------|
| **H100 SXM** | 80GB | Hopper | 현재 On-Prem AI 서버의 주류 |
| **H200 SXM** | 141GB | Hopper | HBM3e, 대역폭 대폭 향상 |
| **B200 SXM** | 192GB | Blackwell | 최신 세대, 대형 모델 풀옵션에 유리 |
| **A100 80GB** | 80GB | Ampere | 구축 완료된 구형 서버에서 주로 사용 |
| **RTX 4090** | 24GB | Ada | 30B 미만 양자화 모델 실험용 |

**멀티 GPU 서빙**

단일 GPU VRAM을 초과하는 모델은 여러 GPU에 모델을 분산합니다:

```
[297B 모델, FP16] → 필요 VRAM ≈ 297 × 2 × 1.2 ≈ 713GB
→ H100 80GB × 8 = 640GB → 부족 (양자화 필요)
→ H200 141GB × 8 = 1,128GB → 풀옵션 서빙 가능
→ B200 192GB × 4 = 768GB → 절반의 카드 수로 풀옵션 가능
```

## 3. 모델별 실전 성능 (직접 서빙해본 결과)

> **배경:** 국내 금융권 및 대기업 On-Prem AI 구축 프로젝트에서 직접 다양한 오픈소스 모델을 서빙하고 Agentic RAG 시스템을 붙여본 경험을 정리했습니다. 회사명은 공개하지 않습니다.
>
> **⚠️ 주의:** 이하 모델 평가는 **Agentic RAG 시스템 구현 목적으로 직접 서빙하며 체감한 개인적인 평가**입니다. 레딧 등 커뮤니티에는 동일 모델에 대해 긍정적인 사용 경험도 많습니다. 사용 목적과 환경에 따라 체감 품질이 크게 다를 수 있으니 참고로만 활용하세요.

### 테스트 기준

평가 기준은 단순 Q&A 성능이 아니라 **Agentic RAG 시스템에서의 실용성**이었습니다:
- Tool calling (도구 이름/인자 정확 생성)
- JSON 출력 일관성 (형식 붕괴 없이 계획 생성)
- 긴 컨텍스트 유지 (대화가 길어질 때 앞 내용 기억)
- Few-shot 학습 (예시를 주면 패턴 따라오기)

---

### GPT-OSS-120B (H100 2장 이상 필요)

**서빙 환경:** H100 SXM × 2, FP16

**솔직한 평가: 기대보다 훨씬 실망스러움**

파라미터 수로 보면 Claude나 GPT-4와 대등한 수준을 기대할 수 있을 것 같지만, 실제 Agentic 시스템에 붙여보면 차이가 극명하게 드러납니다.

```
[증상 1] 컨텍스트가 길어지면 망각과 환각이 급격히 심해짐
→ 대화 3~4턴 이후부터 앞에서 한 말을 무시하기 시작
→ 도구 호출 결과(Observation)를 컨텍스트에 넣어줘도 활용 못 함

[증상 2] JSON 출력이 불안정
→ Few-shot 예시를 아무리 잘 작성해도 형식이 중간에 무너짐
→ "반드시 JSON만 출력"을 명시해도 자연어가 섞이는 케이스 빈번

[증상 3] 추론 자체의 품질 한계
→ 단순한 단일 도구 호출은 가능하지만
→ 도구 간 의존성이 있는 계획(depends_on 관계)을 정확히 수립 못 함
→ "먼저 날씨를 조회하고 그 결과로 알림을 보내라"는 2단계 계획도 자주 실패
```

체감상 GPT-3 초기 서비스 수준 정도의 퀄리티였습니다. 120B라는 숫자에 속지 말 것.

**결론:** Agentic RAG의 핵심인 **Tool Calling + Multi-step Planning에는 부적합**. 단순 문서 Q&A 정도만 가능.

---

### Qwen-3.5 27B / Gemma-30B (H100 1장 필요)

**서빙 환경:** H100 SXM × 1, FP16

GPT-OSS-120B와 방향성은 비슷합니다. 120B보다 파라미터가 훨씬 적으니 성능도 그에 맞게 낮습니다.

```
- 단순 RAG (검색 → 단일 질문 답변) 수준은 무리 없이 동작
- Tool Calling: 도구 1개를 호출하는 것은 가능, 2개 이상 체이닝은 불안정
- 한국어 이해/생성: 모델에 따라 편차가 큼 (Qwen이 한국어 상대적으로 나음)
- 비용 관점에서는 합리적이나, Agent 시스템 구현에는 역부족
```

**결론:** 가볍게 기능 데모하거나 단일 도구 RAG 챗봇 정도에는 활용 가능. Multi-Agent 구현은 어려움.

---

### Qwen-3.5 297B — 풀옵션 (양자화 미적용, H200 8장 필요)

**서빙 환경:** H200 SXM × 8 (권장 스펙인 H100 × 8로는 VRAM 부족으로 불가)

**체감 결과: 앞선 모델들과는 다른 수준, 단 여전히 클라우드와 격차 있음**

```
[개선된 점]
✅ 컨텍스트 유지력: 10턴 이상의 대화에서도 앞 내용을 비교적 잘 기억
✅ JSON 출력 안정성: 95% 이상 케이스에서 형식 준수
✅ Tool Calling: 단일 도구는 물론, 2~3단계 의존성이 있는 계획도 대부분 성공
✅ Few-shot 반응: 예시를 주면 패턴을 잘 따라옴

[여전히 아쉬운 점]
⚠️ 복잡한 재계획(Replan) 시나리오에서 종종 실패
⚠️ 엣지 케이스(예: 도구 실패 후 대안 계획)에서 클라우드 모델 대비 안정성 낮음
⚠️ 응답 속도: 8 GPU 서빙임에도 클라우드 API 대비 체감 느림
```

**Claude 3.5 대비 수준:** 체감상 Claude 3.5 보다 조금 아래 수준. 단순한 업무에는 충분히 쓸 수 있으나 복잡한 Agentic 시나리오에서는 여전히 차이가 납니다.

**결론:** On-Prem에서 현실적으로 Agentic RAG를 구현하려면 이 정도 규모(~297B 이상, 양자화 없음)의 모델이 필요합니다. 단, 비용이 문제입니다.

---

### 모델 규모별 실전 요약

| 모델 규모 | 최소 GPU 구성 | Agentic RAG 적합도 | 현실적 용도 |
|-----------|--------------|-------------------|------------|
| ~30B (Gemma-30B, Qwen 27B 등) | H100 × 1 | ❌ 부족 | 단순 RAG Q&A, 데모 |
| ~120B (GPT-OSS-120B 등) | H100 × 2+ | ❌ 기대 이하 | 단일 도구 RAG, 제한적 활용 |
| ~297B FP16 (Qwen-3.5-297B 등) | **H200 × 8** | ⚠️ 가능 (제한적) | 실무 수준 Agentic RAG |
| Cloud (Claude 3.5, GPT-4o 등) | 해당 없음 | ✅ 권장 | 복잡한 Multi-Agent, 프로덕션 |

> **핵심 인사이트: 오픈소스 모델은 파라미터 수가 클수록 그냥 좋습니다.**
>
> 논문 수준에서는 "특정 task에 파인튜닝된 소형 모델이 대형 모델을 이길 수 있다"는 결과가 나오기도 합니다. 틀린 말은 아닙니다. 그런데 실무에서는 그 "특정 task"의 요구사항이 늘어나고 대화가 길어지는 순간, 소형 모델의 성능은 수직 낙하합니다. Agentic 시스템처럼 복잡도가 높은 환경에서는 파라미터가 클수록 유리한 게 맞고, 이건 직접 서빙해본 결과입니다.

## 4. Agent 시스템에서 모델에게 필요한 것 — 그리고 On-Prem의 현실

### "총과 칼을 쥐어줬더니 울기만 한다"

Agentic RAG 강의에서 이런 표현이 나옵니다:

> **AI 에이전트 = 똑똑하지만, 개발자가 준 장난감(도구)으로만 노는 시스템**

그런데 On-Prem 오픈소스 모델로 이걸 실제로 구현하다 보면, 비유가 조금 달라집니다.

```
[Cloud SaaS 모델 — Claude, GPT-4o]

총과 칼(Tool)을 쥐어주고 "전쟁놀이 해봐"라고 하면:
→ 17살 이상의 성인처럼 이미 뭔지 알고 알아서 전쟁놀이를 합니다.
→ 더 잘하는 경우엔 "저 총이랑 칼 써도 될까요?" 하고 먼저 물어봅니다.

[On-Prem 오픈소스 모델]

같은 총과 칼을 쥐어주고 "전쟁놀이 해봐"라고 하면:
→ 2~5살짜리 아이입니다. 그냥 웁니다.
→ 그래서 개발자가 총과 칼의 사용 설명서를 만들고,
   전쟁하는 영상도 찍어서 보여주고,
   별의별 방법으로 설명을 해줘야
   그제서야 흉내라도 냅니다.

Gemma-30B   ≈ 2살 → 아무리 설명해도 울기만 함 (Tool Calling 자체가 불안정)
GPT-OSS-120B ≈ 4살 → 설명하면 잠깐 따라하다가 다시 엉뚱한 짓 (긴 대화에서 무너짐)
Qwen-3.5-297B ≈ 12살 → 설명하면 어느 정도 하지만, 복잡한 상황에서 판단 미숙
Cloud 모델  ≈ 17살+ → 설명 없이도 하고, 스스로 판단해서 먼저 물어보기도 함
```

### 문제는 "복잡도 폭발"

작은 모델이 도구를 이해하게 만들려면, 개발자 입장에서 **엄청난 공을 들여야** 합니다.

```
[Cloud 모델로 구현할 때]
- 시스템 프롬프트에 도구 목록 + 간단한 사용 예시
- 모델이 알아서 추론해서 도구 선택 및 실행

[소형 On-Prem 모델로 구현할 때]
- 도구마다 상세 사용 설명서를 프롬프트에 추가
- 입력/출력 형식 예시를 10개 이상 박아줘야 함
- 체이닝 방법, 의존성 처리 방법을 전부 예시로 설명
- 그래도 실패하면 재시도 로직, 예외 처리 로직 강화
- 그래도 실패하면 에이전트를 더 잘게 쪼개서 단순화
- ...

결과: 100줄이면 됐을 에이전트가 1,000줄짜리 복잡한 시스템이 되고,
      이걸 다른 개발자가 이해하려면 엄청난 러닝커브가 생깁니다.
```

**현장에서 확인한 실패 패턴:**

```python
# Cloud 모델: 이 정도 2단계 계획을 자연스럽게 수립
plan = {
  "tasks": [
    {"id": "t1", "tool": "rag.query", "args": {"query": "..."}},
    {"id": "t2", "tool": "notification.send",
     "args": {"message": "{{t1.result}}"},
     "depends_on": ["t1"]}
  ]
}

# 소형 On-Prem 모델이 실제로 만들어내는 것들:
# - depends_on 개념을 이해 못 하고 t1, t2를 동시에 실행하려 함
# - t1 결과를 참조해야 할 자리에 그냥 고정 문자열을 채워버림
# - 아예 JSON 구조 자체가 중간에 무너짐
# - 긴 컨텍스트에서는 앞에서 정의한 도구 목록을 잊어버림
```

### 에이전트 성숙도 레벨별 현실

```
Level 0: 단순 Q&A
Level 1: 단일 도구 호출
Level 2: 다단계 도구 체이닝 (의존성 관리)
Level 3: 동적 재계획 (도구 실패 시 대안 수립)
Level 4: 자율적 목표 분해
```

| 레벨 | Gemma-30B | GPT-OSS-120B | Qwen-3.5-297B FP16 | Cloud 모델 |
|------|-----------|--------------|--------------------|-----------|
| Level 0~1 | 가능 | 가능 | 가능 | 가능 |
| Level 2 | ❌ 울기만 함 | ❌ 불안정 | ⚠️ 대부분 가능 | ✅ 안정적 |
| Level 3 | ❌ | ❌ | ⚠️ 제한적 | ✅ 가능 |
| Level 4 | ❌ | ❌ | ⚠️ 제한적 | ✅ 가능 |

### On-Prem Agent의 현실

이게 결국 어떤 상황으로 이어지냐면:

```
[이상]
모델이 충분히 똑똑하니까 
→ 개발자는 도구와 울타리만 잘 설계하면 됨
→ Agent 완성도 높음

[현실 (On-Prem)]
모델 능력이 부족하니까
→ 개발자가 모델 부족분을 코드와 프롬프트로 때워야 함
→ 시스템 복잡도 폭발
→ Agent 완성도: 100명 중 5명이 만족하는 수준
→ 개발자도 답답하고, 쓰는 사람도 불만
→ 그래도 On-Prem이라 어쩔 수 없다는 면피
```

**더 솔직하게 말하면:**

충분한 성능이 나오는 모델(~297B FP16)을 서빙할 인프라를 갖춘 회사는 극히 드뭅니다. H200 8장 서버를 실제로 구축하고 운영할 수 있는 곳이 얼마나 되겠습니까. 그러다 보니 현장에서 벌어지는 일은 이렇습니다:

> 감당 가능한 인프라(H100 1~2장) → 올릴 수 있는 모델(30B~120B) →  
> Level 2도 불안정한 Agent → 프롬프트 수백 줄로 때우기 → 복잡도 폭발 →  
> 그나마 동작하는 최소한의 시스템으로 납품 → 완성도는 포기

이게 지금 많은 On-Prem AI 프로젝트의 실제 모습입니다.

그리고 이걸 알고 있어야 On-Prem 프로젝트에서 **기대 수준을 현실적으로 설정**하고, **어디에 힘을 쓸지 올바른 판단**을 내릴 수 있습니다.

## 5. On-Prem에서 일하게 됐다면

On-Prem 환경이 주어진 상황에서 Agentic RAG를 구현해야 하는 개발자를 위한 실전 조언입니다.

**1) 가능하다면 Cloud로 먼저 검증하세요**

On-Prem 오픈소스 모델로 처음부터 시작하면, 모델 품질이 낮아서 **"Agentic 시스템 설계가 잘못된 건지, 모델 능력의 한계인지"** 구분이 안 됩니다. 환경이 허락한다면 Claude나 GPT-4o로 먼저 잘 동작하는 시스템을 만들고, 그 다음 모델을 교체해서 성능 차이를 정량화하는 순서가 가장 효율적입니다.

**2) "120B면 충분하지 않을까?"는 대부분 틀립니다**

Agentic 시스템에서 Tool Calling과 Multi-step Planning을 안정적으로 돌리려면 현재 기준 **200B 이상, 양자화 없이**가 사실상 최소입니다. 인프라 한계로 그보다 작은 모델을 써야 한다면, Agent의 복잡도를 낮추거나 단일 도구 위주로 설계하는 게 현실적입니다.

**3) 양자화는 Agentic 능력을 직접 갉아먹습니다**

INT4 양자화로 메모리를 절약하면, JSON 생성 안정성과 긴 컨텍스트 유지력이 먼저 무너집니다. 이 두 가지가 Agentic 시스템의 핵심이라는 점에서 양자화와 Agent 완성도는 거의 반비례합니다.

**4) 서빙 프레임워크 선택**

모델을 GPU에 올리는 것과 "빠르고 안정적으로 서빙하는 것"은 다른 문제입니다.

```
vLLM              → 처리량(throughput) 최적화, 프로덕션 표준
Ollama            → 개발/테스트 빠른 세팅, 로컬 실험용
TGI (HuggingFace) → 다양한 모델 지원, 유연성
```

**5) 오픈소스 모델은 빠르게 발전하고 있습니다**

지금 120B 모델의 한계가 1~2년 뒤에는 30~40B 수준에서 해소될 가능성도 있습니다. On-Prem 환경이 주어졌다면 지금 당장의 완성도보다는 **모델 교체에 유연한 구조**로 시스템을 설계해두는 게 장기적으로 훨씬 유리합니다.

## 마무리

이 문서의 핵심 질문은 하나였습니다:

> **"클라우드에서 Claude/GPT-4로 만든 Agentic RAG를, On-Prem 오픈소스 모델로 그대로 재현할 수 있을까?"**

직접 서빙해본 솔직한 답은 이렇습니다.

**현재는 어렵습니다.** 모델 능력의 격차가 분명히 있고, 그 격차를 코드와 프롬프트로 메우다 보면 시스템 복잡도가 폭발합니다. 충분한 성능의 모델(~297B FP16)을 올릴 인프라를 갖춘 곳도 극소수이고, 그런 인프라 없이 만든 On-Prem Agent의 완성도는 현실적으로 한계가 있습니다.

**그렇다고 포기할 필요는 없습니다.** 오픈소스 모델은 놀라운 속도로 발전하고 있고, 지금의 격차가 영원하지는 않습니다. On-Prem 환경에서 일하게 됐다면, 모델의 한계를 정확히 파악하고 그 안에서 최선의 시스템을 설계하는 것 — 그게 이 문서를 쓴 이유입니다.
